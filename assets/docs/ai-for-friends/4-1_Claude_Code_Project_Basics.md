## Overview

By the end of this lesson, you will understand what a Claude Project is, name its three parts, and decide what recurring work your first Project should cover. A Project is a dedicated workspace you set up once and reuse in every chat.

### Why This Matters

A plain chat starts from a blank slate every time. You re-explain your job, re-paste your templates, and re-state your rules on each new conversation. A Project ends that repetition. It holds your standing instructions and your reference documents in one place, so every chat inside it gets to work immediately.

- A Claude account (claude.ai)

## Step 1: The Three Parts of a Project

A Project is a dedicated space on claude.ai built around one kind of recurring work. It has three parts: a name, custom instructions, and Project knowledge. Learn what each part does and you understand the whole tool.

### What You'll Do

You will learn the three parts of a Project and which two of them do the real work.

### Instructions

1. Read the three parts in the table below.
2. Note that the name is just a label, while the other two parts change how Claude behaves.
3. Focus on custom instructions and Project knowledge. These are the two that matter.
4. Keep these three parts in mind as you plan your first Project in Step 3.

### Key Concepts

| Part | What It Is | What It Does For You |
|------|-----------|----------------------|
| **Name** | A short label for what this Project is for (e.g., "Recruiting Assistant") | Helps you find the right Project in your sidebar |
| **Custom instructions** | Plain-language standing rules that tell Claude who it is, how to behave, and how to format answers | Written once, they apply to every chat inside the Project |
| **Project knowledge** | Reference files you upload (templates, style guides, policies, past examples) | Claude can draw on them in any conversation without you re-attaching |

<!-- INFO: The Shape of a Project | A Project is a folder-shaped workspace inside claude.ai. You set it up once — what it is for, how it should behave, what documents it should know about — and every chat you start inside it inherits all of that automatically. -->

<!-- INFO: The Two That Matter | The custom instructions are the standing orders. The Project knowledge is the reference shelf. Together they mean you stop repeating yourself. -->

## Step 2: Why a Project Beats a Blank Chat

A plain chat forgets you the moment it ends. A Project remembers. Understanding the difference tells you when a Project is worth setting up and when a quick chat is enough.

### What You'll Do

You will compare a plain chat to a Project side by side and learn the one test that tells you when to build a Project.

### Instructions

1. Read the two columns below.
2. Notice what you repeat in every plain chat.
3. Notice how a Project removes each of those repeated steps.
4. Apply the test in the tip to your own work.

### Plain Chat vs. Project

Think of it as the difference between calling a random person for help and calling YOUR assistant. The random person needs the whole backstory every time. Your assistant already knows your role and gets straight to work.

<!-- COLUMNS: 50/50 -->

**Every new plain chat:**

- You re-explain your role from scratch.
- You re-paste your templates and examples.
- You re-state your formatting rules.

<!-- COLSEP -->

**Every chat inside a Project:**

- Your instructions are already in effect.
- Your documents are already available.
- You have one dedicated space for this work.

<!-- /COLUMNS -->

<!-- TIP: The Test | If you find yourself pasting the same context into a chat twice, that context belongs in a Project. Set it up once and stop repeating yourself. -->

## Step 3: Decide What Your First Project Is For

A Project works best when it covers one kind of recurring work. Before you build anything, decide what that work is. The examples below show how five roles scope a first Project.

### What You'll Do

You will pick the recurring work your first Project will cover, using the role examples as a guide.

### Instructions

1. Read the five role examples in the table below.
2. Find the row closest to your own work.
3. Name the recurring task you handle most often.
4. Write down that one kind of work. It becomes the purpose of your first Project.

### Key Concepts

| Role | Project Name | The Recurring Work It Covers |
|------|-------------|------------------------------|
| Legal | Contract Review | Clause review, risk flagging, tracking defined terms |
| Marketing | Content Assistant | Repurposing content, enforcing brand voice, campaign summaries |
| Industrial Engineering | Process & Work-Order Assistant | Nonconformance summaries, standard-work drafting, work-order status tracking |
| International Relations | Diplomatic Affairs Assistant | Briefing memos, protocol checks, agreement and cable tracking |
| HR (Recruiting) | Recruiting Assistant | Candidate summaries, outreach messages, pipeline tracking |

<!-- NOTE: One Kind of Work Per Project | Keep each Project to a single kind of recurring work. A Project that tries to do everything follows no clear set of rules. When you have a second kind of work, build a second Project. -->

<!-- TIP: Name It After the Work | Name your Project after the recurring task, not after yourself. "Contract Review" tells you what belongs inside it. "My Project" does not. -->
